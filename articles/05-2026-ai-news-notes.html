这一周的 AI 新闻，我只想记三件事

2026 年 10 月中：开源多模态大模型、MCP 无状态规范与企业落地、协议从演示走向治理——三件对做 AI 产品真正有影响的公开动态。

又到周末，信息流里全是「重磅」。做产品的人若每条都追，会被追着跑；若完全不看，又会在评审里突然语塞。我的办法很土：每周只允许自己认真记下三件事。三件之外，可以浏览，不许写进工作判断。

这一周（相对 2026 年 10 月中旬）我记下的三件，都来自可核对的公开报道。下面每件分两段：事实尽量短，判断归我自己。数字若公开材料写得很细，我只取对产品决策有用的部分；拿不准的，我会写「据公开报道」，避免装成一手数据。

第一件：开源多模态，又把「能不能自己部署」往前推了一步

据 Meta 公开博客（2026 年 10 月 15 日），公司发布了开源权重模型 Muse Spark Open，定位强调原生多模态与长程 Agent 式任务。公开材料里提到的量级大致是：总参数约 816B、每 token 激活约 42B，上下文可达约 1M tokens；输入可含文本、图像、音频与视频，输出以文本为主。同时强调面向编程与工具调用类工作流，并提供多种云与本地推理路径；也提到在 Apple 硅上的桌面级运行尝试（公开文案涉及高端 Mac Studio 组合）。

我记这件事，不是为了背参数。参数战每周都有。我想记的是产品含义：

开源权重 + 多模态 + 长上下文，会改变企业内部助手的默认架构选项。以前「看图说话、听录音纪要、对着设计稿改需求」常常要拼多套专用模型与脆弱胶水；现在公开路线越来越鼓励「一个主模型吃多种输入」。对产品经理，这意味着需求里更该写清：哪些模态是一等公民，哪些只是附件；隐私上，截图与录音是否允许出域；长上下文是用来少检索，还是用来容纳更长轨迹。

第二层判断：开源降低的是「获得能力」的门槛，不是「治理能力」的门槛。权重可下载，不代表你可以在合规框架里直接用；许可条款、安全评测、商业限制仍要法务与安全一起看。据公开报道，该模型附有专门许可与安全说明——具体条款以官方页面为准，我这里不替读者做法律结论。

第三层：桌面级可运行的叙事在加强。对个人站和中小团队，这意味着「重推理必须上云」不再是唯一心理默认。但对真正的企业生产，我仍会先问观测、权限、审计，而不是先问能不能插两台主机。能跑起来，和能负责任地跑，差的是产品结构，不是风扇噪音。

一句话留给自己：多模态开源会让 Demo 更好看；你的差异化仍在资料、权限与出错怎么修。

第二件：MCP 变成「可运维的协议」，而不只是「能连上的插件」

Model Context Protocol（MCP）这条线，2025 到 2026 年已经从开发者玩具感，走到了平台标配感。这一周我真正想记的，是规范与企业落地两边同时传来的信号。

据 MCP 官方博客，2026-07-28 规范把协议核心推向无状态的请求/响应模型：弱化协议级会话与握手负担，让服务更容易放在负载均衡、无服务器和边缘形态上；同时加强授权相关约束，并把部分能力推进正式扩展机制。Anthropic 等客户端侧也公开表示在产品中推进对该规范的支持。另据公开报道，生态里的 SDK 下载量已到非常高的月级规模——具体数字以官方披露为准，我只取方向：这东西不再是小众实验。

同一周附近，Google 开发者博客（2026 年 10 月 14 日）介绍了 Apigee hybrid 上的 MCP 能力：把已有 API（经 OpenAPI 描述）暴露为 Agent 可发现、可调用的工具，并且在 hybrid 模式下，MCP 数据面跑在客户自己的 Kubernetes 集群里；公开要点包括请求路径不出集群、配置由集群侧拉取、以及沿用既有 API 产品化与配额治理。对我这种做过 B 端的人，这才是「协议长大了」的味道——长大的标志不是又多一个 Demo 连接器，而是安全团队开始问流量走哪、审计怎么做、工具发现是否按权限过滤。

产品判断三条：

其一，工具连接会商品化，差异回到「你暴露哪些工具、如何鉴权、如何计量」。 以前团队可能以「我们写了 MCP Server」为傲；接下来这可能像「我们提供了 HTTP API」一样普通。普通之后，比的是治理。

其二，无状态化会逼你把「会话状态」设计得更显式。 协议不帮你偷偷记会话了，业务若需要跨步状态，要用可传递的句柄、任务对象、草稿 ID。这对 PRD 是好事：状态终于不能藏在连接里。

其三，企业会问「能不能在我的地界跑」。 hybrid、私网、数据驻留这些词，会从基础设施会议进产品会议。做 Agent 平台的同学，最好提前准备一页：工具调用的数据面在哪、日志在哪、谁有权关工具。

一句话：MCP 的下一阶段，是运维与治理，不是又一个「五分钟接入」教程。

第三件：大厂把「Agent 的手」往工作流与管理面伸

第三件我记的不是单一发布，而是一种合在一起才明显的趋势：模型当然还在发，但更密集的是「Agent 能在哪些办公与云工作流里动手」，以及「管理员如何管这些手」。

据公开的产品更新与开发者材料（2026 年 10 月中一带），能看到几类动作并行：对话产品侧继续加强自定义 MCP 应用与管理发布控制；办公与企业套件侧推进工作流搭建、连接器与权限相关能力；开发者工具侧继续改 Agent 权限预设、本地 MCP 启停与修复体验。同一时期，语音/图像/视频生成类服务也在把能力封装进 MCP，让助手在常用工作界面里直接调用多模态生成——例如 ElevenLabs 等厂商公开介绍其 MCP 对语音、音乐、图像与视频生成的支持。另有开源社区把 ComfyUI 工作流暴露为 MCP 工具，方便本地或云端由 Agent 调度。

我不敢把每一条更新的版本号当成战略结论——版本号会过时。我想记的是产品结构变化：

「模型」越来越不是用户购买的唯一对象，「可管理的工具权限包」才是。 谁能安装连接器、谁能发布到企业目录、默认是否可写、是否要二次确认——这些管理面问题，正在变成和模型质量同等重要的卖点。

对个人站作者和甲方产品经理，含义略有不同。对我自己做产品：设计功能时要默认带上管理员故事，而不是只设计终端用户故事。对选型：比「哪个模型更聪明」更常问「权限模型能否对接我们的 IdP、审计能否导出、能否按工具配额」。

还有一个体感：多模态生成进入 MCP 之后，内容安全与品牌风险会从「专门的设计工具」渗进「普通助手」。员工随口一句「帮我做张活动图并发到群里」，链路可能已经跨过生成、存储、发送。PRD 若不写发送边界，出事时你说「我们只是接了 MCP」，对外不够用。

一句话：Agent 的手在变长；产品文档里的「手能伸到哪」要写得比模型名片更清楚。

三件事串起来，我看到的主线

开源多模态降低能力获得成本；MCP 无状态与企业落地降低工具接入与治理成本；大厂工作流把这些能力塞进日常软件。主线不是「又更智能了」，而是「智能开始像水电一样被接进管路」——管路有阀门、有电表、有检修口，才会有人敢用。

回到我自己的栏目定位：我是 AI 产品经理，不是新闻搬运工。新闻的用处，是校正我下周写需求时的默认假设。这一周我校正了三条假设：

  1. 默认假设从「多模态要拼多模型」略调向「单主模型多输入可讨论」，但仍坚持模态的隐私分级。
  2. 默认假设从「有 MCP 就够炫」调向「MCP 必须可观测、可鉴权、可关停」。
  3. 默认假设从「先追模型」调向「先追管理面与写操作边界」。

我不记的是什么

刻意不记的，通常是：无法核对的排行榜、营销味很重的「全面超越」、以及跟我当前产品决策无关的八卦。不是它们一定假，是它们占用判断带宽。判断带宽是产品经理的库存，库存要留给可执行的变化。

若你也做 AI 产品，不妨试同款约束：每周三件事，事实与判断分开写。写多了会发现，真正影响路线的新闻并不多；大多噪声只是在贩卖焦虑或优越感。

结尾

2023 年我害怕模型会写文档；2024 年我劝人别只做聊天框；2025 年初我写出错怎么修；2025 年我改 Agent 的需求写法。到 2026 年秋天，新闻还在加速，我的方法却在减速——减速到每周三件。

减速不是摆烂。是把注意力从「发生了什么」夺回「我因此改什么」。改不了自己产品假设的新闻，看过等于没看。

这一周三件事：开源多模态、MCP 的运维化、Agent 之手的管理面。下周若它们仍影响我写 PRD，就留下；若只是刷过而已，就让它们过去。

这三件事分别改我下周的哪一页文档

新闻若不落到文档变更，就只是谈资。我强迫自己写「改哪一页」。

对第一件（开源多模态）：检查进行中的助手需求，是否把「截图/录音输入」写成了例外附件。若业务确实需要，补隐私分级与留存周期；若不需要，明确关闭入口，避免灰着上线。

对第二件（MCP 无状态与企业落地）：把连接器需求里的「支持 MCP」改成可测条目——鉴权方式、工具列表是否按角色过滤、故障时如何摘除单个工具、日志是否含工具名与调用结果摘要。以前写「接入 MCP」就算完成，从这周起不算。

对第三件（管理面与多模态工具）：在管理员故事里补「发布/停用连接器」「默认只读」「写操作二次确认」三节。没有管理员故事的 Agent 功能，排期往后挪。

三页文档的改动，比转发三篇热文有用。

和 2023–2025 那几篇的对照

回看自己更早的专栏节奏，会发现主题其实在收敛：从害怕表达贬值，到强调有据生成，到强调容错，到强调 Agent 契约，再到用新闻校正契约的默认假设。表面是五年五篇，内里是同一件事：当生成与行动变便宜，产品经理要更贵地出售「约束与责任」。

约束不是为了虐模型。是为了让组织敢把真流量交给它。新闻加速的是能力供给；专栏想守住的是需求侧的消化能力。消化不了的能力，会变成演示债务。

阅读公开材料时的个人纪律

再补几条我自己的阅读纪律，免得「据公开报道」变成免责口头禅：

  • 优先读官方博客与规范文档，其次才是二手解读；
  • 参数与下载量若用于对外文章，能不写就不写死，写则指向来源日期；
  • 把「即将」「计划中」「研究预览」和「已正式可用」分开；
  • 涉及安全与许可，不给读者操作建议冒充法律意见；
  • 同一周多条新闻若指向同一结构变化，合并记一件，避免清单膨胀。

纪律让我每周真的只留下三件。三件写透，胜过三十件标题党。

若你只看摘要

这一周我记住的三件事：

  1. 开源多模态大模型继续把「可自部署的强能力」推到台前——能力易得，治理仍难。
  2. MCP 规范无状态化，并进入企业 API 治理场景——协议进入运维时代。
  3. Agent 的手伸进工作流时，管理面与写边界成为产品一等需求。

我因此改的不是朋友圈文案，是需求文档里的几行可测句子。

写给 lidyapm.com 的读者

如果你也是一个人维护产品判断，经不起每天被信息流打断：用「每周三件」当过滤器吧。过滤器的出口，应该是你自己的产品假设列表，而不是收藏夹。收藏夹会膨胀；假设列表应当可被下周新闻证伪。

我愿意被证伪。证伪说明自己还在更新。比准确更可怕的，是一年后仍用过时假设写着看起来很新的 PRD。

补记：我如何核对「这一周」

写这篇前，我查了几类公开来源：模型方研究博客、协议官方说明、云厂商开发者博客，以及汇总周报。互相能印证的，才进入「三件事」；只有营销稿复述的，先放观察名单。

例如 Muse Spark Open，以 Meta 研究博客与汇总介绍交叉看；MCP 2026-07-28，以协议博客与客户端跟进说明交叉看；Apigee hybrid 的 MCP，以 Google 开发者博客为准。涉及「月下载量」这类易变统计，我在正文避免写死成口号，只保留「规模已很大」的方向判断。

核对不是学术洁癖。是因为个人站文章会被人当参考：写错一个「已正式可用」，可能让读者在公司里讲错话。讲错话的成本，比我少写两句爽文高。

三件事之外的边角，为什么不进正册

边角其实不少：桌面客户端的管理策略变更、某办公套件技能（skills）的灰度、某编码助手的预测输入实验……它们可能影响特定用户，但尚未改变我「默认怎么写需求」的假设。于是它们留在备忘，不占三件名额。

名额制度的好处是残酷：逼你排序。排序是产品经理本职。连新闻都不能排序的人，很难在需求里排序。

给团队同步的一分钟版

若你要在周一会上讲：

「上周开源多模态又进一步，我们继续盯隐私与自部署治理，不追参数。」 「MCP 规范与企业落地都在强调无状态和可治理，我们的连接器验收改成按工具鉴权与可关停。」 「Agent 管理面成为卖点，我们本周补管理员故事与写操作确认。」

一分钟讲完。讲完就改文档。不改文档的同步，是气氛组。

我仍保持谨慎的地方

公开材料再热闹，也不等于你的用户就绪。中小商家可能还在为客服排班发愁；大企业可能卡在采购与安全评估。新闻的时间，和客户的时间，不是同一时区。产品经理要活在客户时区，同时用新闻校正地图。

另外，开源与协议的繁荣，也可能带来「集成表面繁荣、责任真空」。谁对工具链最终结果负责？谁对模型输出负责？合同与产品文案要写明。新闻不会帮你写责任条款。

若三件事要排优先级

对正在做企业助手的人，我建议优先级是：第二件（MCP 治理）> 第三件（管理面）> 第一件（开源多模态）。原因很功利：多数团队短期不会换成最新开源巨模型，但几乎都会接到「再加一个工具/连接器」的需求。工具治理与管理面，是本周就能改的；换模型是季度级议题。

对正在做消费级多模态娱乐的人，优先级可能反转。请按自己的产品，不要按我的栏目。我的排序只对「B 端助手 + 工具调用」默认读者负责。

结束前的自我检查

写完三件事，我问自己：有没有编造未核对的数字？有没有把预览写成正式？有没有用情绪词代替判断？有没有给出可执行的文档改动？四问过了，才允许发布到 lidyapm.com。

专栏不是情绪出口，是判断训练。训练要有动作：改假设、改文档、改验收。动作缺席的一周，就算记了三十件事，也算空周。

下一周预留的观察位

我给下周预留了两个观察位：一是各家客户端对 MCP 新规范的实际完成度；二是开源多模态在真实编程/办公任务上的第三方复现评测。有扎实复现再升级判断；没有就继续观察。观察也是一种产品能力——不是每条热搜都值得改路线。

把观察位写下来，是为了防止自己被下一波标题拖走。标题擅长制造「必须立刻」；产品路线擅长「可以等证据」。

新闻会过期，方法可以留下。若你读到这篇时，某一件具体产品已经改名或迭代，请仍用「事实 / 判断 / 我改哪页文档」的结构自己重写三件——那才是这篇文章想交给你的东西。

方法在，专栏才站得住。
